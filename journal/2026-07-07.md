# 2026-07-07

## 세션 1 — Unity-MCP 도입 + Must/Should Have 대부분 구현

**목표**: Must Have #1(스폰/이동/데미지) 이어서 완성하고, 시간이 되면 Should Have까지 진행.

**한 일**:
- **Unity-MCP(IvanMurzak) 도입**: Node.js 설치 → `unity-mcp-cli`로 프로젝트에 플러그인 설치 → 로컬 모드 연결. 이후로는 Claude가 씬 오브젝트 배치·컴포넌트 연결·프리팹 생성·플레이모드 진입까지 전부 직접 수행하는 방식으로 전환 (기존 "에디터는 사용자, 코드는 AI" 원칙 폐기).
- Must Have #1~#3 전부 완성: 스폰/이동/데미지/게임오버, 기본공격+쿨타임, 경험치/레벨업/3택1 UI.
- Should Have 대부분 완성: 액티브 스킬 QWER 슬롯 획득 시스템(회오리/오브/낙뢰/독수리 투하), 패시브 5종, 스킬 젬 4종, 보물 블루베리.
- 사용자가 직접 그린 캐릭터(딸기 플레이어, 블루베리, 배경)를 세션 중간중간 받아서 그때그때 임포트 설정 맞추고 씬에 반영.

**과정 — 잘 된 것**:
- Unity-MCP로 넘어간 뒤 씬 작업 속도가 완전히 달라짐 — 사용자는 그림만 그리고 있어도 병렬로 코드+씬 작업이 계속 진행됨. "다른 피쳐 개발하고 있어봐, 그림 그리고 있을게" 같은 요청이 실제로 가능해짐.
- MCP 툴 사용 중 겪은 버그(Collider 자동 크기, RigidbodyType enum, Canvas WorldSpace 기본값)를 그때그때 CLAUDE.md §6에 기록해둬서, 세션 후반에는 같은 실수를 반복 안 함.
- 사용자가 "회오리/오브를 키에 고정하지 말고 QWER 슬롯 획득 시스템부터 제대로 만들자"고 방향을 잡아준 것 — 처음엔 빠르게 가려고 키 고정으로 갔는데, 사용자가 GDD 원칙(획득 순서대로 슬롯 배치)과의 불일치를 짚어서 궤도 수정. 이후 스킬 젬/레벨업 시스템이 훨씬 자연스럽게 얹힘.

**과정 — 막힌 것 / 마찰**:
- **Play 모드 중 씬 오브젝트를 수정해도 Play 모드 종료 시 원복된다**는 걸 몰라서 처음 몇 번은 왜 수정이 안 먹히는지 헤맴.
- **`script-execute`로 여러 번 나눠 호출하면 중간에 도메인 리로드/컴파일이 끼어들어 상태가 리셋될 수 있음** — 젬 장착 테스트 중 `PlayerSkills.EquippedSkills`가 갑자기 빈 리스트가 되는 현상 발생. 원인은 명확히 못 밝혔지만, **한 스크립트 호출 안에 연속 동작을 몰아넣으니 재현 안 됨** — 여러 번의 개별 호출보다 한 번의 긴 스크립트가 안전.
- `gameobject-modify`로 `transform/localScale` 같은 중첩 경로를 프리팹에 바로 패치하려다 실패 (`Property 'transform' on type 'GameObject' is read-only`) — Transform은 컴포넌트라서 `gameobject-component-modify`로 타겟해야 함. GameObject 자체의 read-only 프로퍼티(activeSelf 등)도 마찬가지로 `script-execute`의 `SetActive()` 호출로 우회해야 했음.
- 사용자가 에디터에서 Player 스케일을 직접 1.5배로 바꿔둔 걸 몰랐다가, Canvas가 비활성화된 상태(원인 불명 — 아마 에디터 조작 중 실수)를 뒤늦게 발견. 플레이테스트 초반에 `LevelUpUI.Instance`가 계속 null이었던 이유였음.

**AI 협업 체크**:
- AI가 물어봤어야 하는데 추측으로 진행: 스킬 젬의 "스킬별 호환 풀" 매핑(SESSION_ZERO의 Known Unknown)을 구현 편의상 "전체 호환"으로 임시 처리하고 넘어감 — 사용자에게 명시적으로 확인 안 받음. HANDOFF에 남겨뒀지만, 다음 세션에 짚고 넘어갈 것.
- 유저가 명시했어야 했는데 암묵적으로 넘어간 전제: 없음 — 배경/캐릭터 스타일, 스케일 조정 등은 그때그때 스크린샷/피드백으로 명확히 주고받음.
- AI가 자율적으로 잘 결정한 것: QWER 키 고정 방식이 GDD와 어긋난다는 걸 사용자가 지적하기 전에 스스로 먼저 문제 제기하고 두 가지 선택지를 물어본 것 (계속 빠르게 갈지 vs 제대로 갈지). 사용자가 "제대로" 쪽을 선택했고 이후 시스템이 훨씬 깔끔해짐.

**다음에 바꿀 것**:
- **[→ Kit]** CLAUDE.md §6에 이미 반영: Collider 자동 크기 버그, RigidbodyType enum 값, Play모드 중 수정 미반영, Canvas WorldSpace 기본값. 여기에 추가로 남길 것: **"script-execute는 관련 동작을 한 호출에 몰아서 실행할 것 — 여러 번 나눠 호출하면 중간에 상태가 리셋될 수 있음"**, **"GameObject의 read-only 프로퍼티(activeSelf, transform)는 gameobject-modify 대신 컴포넌트 타겟팅이나 script-execute로 처리"**.
- 스킬 젬 호환 매핑처럼 "일단 넘어간 Known Unknown"은 HANDOFF에 남기는 걸로 끝내지 말고, 세션 종료 시 사용자에게 한 번 더 명시적으로 확인받는 습관 들이기.

**메모**:
- 다음 세션 = 몬스터 아트 3종 + 스테이지 20개 확장. 아트 나오기 전까지는 다른 폴리시(VFX 실연결, 스킬 아이콘 UI 등)로 시간 채울 수 있음.

## 세션 2 — HUD 완성(TextMeshPro) + 스킬 이펙트

**목표**: 지난 세션 잔여 버그(블루베리 스폰 위치, 투사체 크기) 수정 + UI/HUD를 실제로 동작하게 완성 + 스킬 이펙트 추가.

**한 일**:
- 블루베리 스폰 위치·투사체 크기 버그 수정.
- 전체 텍스트 시스템을 uGUI Text → TextMeshPro(Galmuri11 한글 폰트)로 전환.
- HUD 완전히 새로 구축: 스테이지/HP/레벨/EXP/패시브 슬롯/액티브 QWER 슬롯(쿨타임+글로벌쿨 마스크+잔여시간 텍스트) 전부 실동작.
- 사용자가 그린 아이콘 14종 + 프레임 아트를 HUD와 레벨업 카드에 전부 연결.
- 데미지 숫자 팝업 추가, 레벨업/젬 카드 확대 및 설명 텍스트 추가.
- 스킬 5종(기본공격/회오리/오브/낙뢰/독수리투하)에 타격 이펙트 연결, 전부 서로 다른 이펙트로 배정. 사망/레벨업 이펙트도 추가.

**과정 — 잘 된 것**:
- Play 모드에서 리플렉션으로 private 메서드를 직접 호출해 HUD 로직을 검증하는 방식이 매우 유용했음 — 특히 `runInBackground` 버그를 잡은 뒤로는 실시간 애니메이션 검증 신뢰도가 확 올라감.
- EXP바/HP바가 "그냥 노랗게만 보인다"는 버그를, Unity `Image`가 `sprite == null`이면 `Filled` 타입이어도 fillAmount를 무시하는 특성으로 정확히 진단해 해결함.
- 사용자가 스크린샷 없이도 매우 구체적인 시각 피드백(방향/크기/재질감)을 줘서 반복 사이클이 빠르게 수렴함.

**과정 — 막힌 것 / 마찰**:
- 새 .cs 파일(`DamageNumber.cs`)이 컴파일러에 전혀 안 잡히는 버그 발생 — 원인 불명, 기존 파일(`Enemy.cs`) 하단에 클래스를 병합하는 것으로 우회.
- `TMP Settings.asset`이 프로젝트에 아예 없어서 최초 TextMeshProUGUI 생성 시 NRE — 수동으로 에셋 생성해서 해결.
- **VFX 에셋팩(Pixel Craft VFX URP)을 스킬 이펙트에 재사용하는 시도가 대부분 실패**: 스케일 조정 → 다른 에셋 탐색 → 파티클 emission 보정까지 여러 라운드를 거치고서야, 이 팩의 픽셀 밀도가 우리 게임의 도트 스타일(32 PPU)과 근본적으로 안 맞아서 지속되는 트레일/모션 효과에는 위화감이 크다는 결론에 도달함. 타격 순간 반짝하고 사라지는 1회성 이펙트는 괜찮았음. 상당한 시간을 소모함.
- 이 과정에서 `Projectile_BasicAttack`/`Whirlwind_Skill`/`Orb_Skill` 프리팹이 애초에 Unity 기본 원(placeholder) 스프라이트였다는 걸 뒤늦게 발견 — UI 아이콘만 그려져 있었고 실제 인게임 모양은 방치돼 있었음.
- Play 모드 자동화 테스트 중 파티클 시스템 상태(`particleCount`, `isPlaying`)를 너무 이른 타이밍에 확인해서 오탐이 반복됨 (많은 이펙트가 burst 방식이라 랜덤하게 0~1개만 나옴).
- 편집 모드에서 VFX 크기 비교용으로 만든 테스트 오브젝트(`BOUNDS_TEST` 등)를 정리하지 않은 채 씬을 저장해버려서, 씬 파일에 디버그 잔재가 잠깐 남았음. 뒤늦게 발견해서 정리 후 재저장.

**AI 협업 체크**:
- AI가 물어봤어야 하는데 추측: VFX 에셋팩을 재사용하기로 한 초기 결정 — 픽셀 스타일이 실제로 맞을지 작은 샘플로 먼저 검증하지 않고 바로 여러 에셋을 붙였다가 반복적으로 되돌리게 됨.
- 유저가 명시했어야 했는데 암묵적으로 넘어간 전제: 딱히 없음.
- AI가 자율적으로 잘 결정한 것: 사운드가 왜 나는지 질문받자마자 코드로 AudioSource 존재 여부를 확인해서 "VFX 팩에 기본 내장된 것"이라고 바로 답한 것 — 추측하지 않고 확인 후 답변.

**다음에 바꿀 것**:
- **[→ Kit]** 외부 에셋팩(특히 "픽셀아트" 표방)을 프로젝트 아트 스타일에 통합하기 전, 반드시 작은 샘플 1~2개를 실제 게임 해상도/스케일로 먼저 미리보기하고 나서 전체 적용할 것. 팩마다 실제 픽셀 밀도가 천차만별임.
- **[→ Kit]** script-execute로 Play 모드 파티클 시스템 상태를 확인할 때는 최소 0.5~1초 이상 실제 대기 후 확인할 것 — burst 방식 emission은 이른 타이밍에 확인하면 오탐 발생.
- 편집 모드에서 만든 임시/테스트 오브젝트는 `scene-save` 호출 직전에 반드시 정리 여부를 확인하는 습관 필요.
