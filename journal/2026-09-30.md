## 세션 1 — 블루베리 디펜스

**목표**: 레벨업 카드를 스킬마다 다르게 재설계하고, 밸런스 판독지 양식을 새로 만든다.

**한 일**: `SkillStat`에 축 13종을 추가하고 소비부를 배선한 뒤, 55개 상태 중 46개의 9칸 구성을 다시 짰다. 피해와 쿨은 재구성 전과 같게 유지했고, 새 카드가 피해 숫자 밖에서 올리는 화력은 피해 목표에서 상쇄했다. 카드 문구 35줄을 세 언어에 넣고 표에 적재했다. 스킬 밸런스 판독지 양식(`balance_readout.html`)을 새로 만들고 `analyze.js`에 연결했으며, 대변인 실행 단계를 루프 문서에 배선했다. 노션 두 페이지를 현재 값으로 갱신했다.

**과정 — 잘 된 것**: 커브 재작성을 스크립트로 하고 **검산을 별도 스크립트로 분리**한 것이 계속 효과를 봤다. 적용기와 검산기가 같은 함수를 쓰지 않으니 배분 로직의 결함이 매번 걸렸다. 슬롯 회계가 어긋나 9칸이 8칸이 된 것, `×1.0`이라 아무 일도 안 하는 카드가 생긴 것, 배율이 `×1.5` 상한을 넘은 것을 전부 검산기가 잡았다.

옆 세션과의 분담도 매끄러웠다. **경계를 "누가 어느 파일을 만지나"가 아니라 "데이터 계약"으로 잡은 것**이 주효했다. 봇이 내보내는 필드 이름을 상대가 확정해서 알려주고 나는 그것을 읽기만 하니, 같은 파일을 동시에 고칠 일이 한 번도 없었다.

**과정 — 막힌 것 / 마찰**: **문체 규칙을 소스 파일 안의 문자열에 적용하지 않았다.** 채팅 답변은 규칙대로 쓰면서 보고서 템플릿의 견본 문장에는 "쿨타임 칸이 죽어 있었고" 같은 구어체를 그대로 썼다. 사용자가 "코드랑 채팅이랑 문구 생성하는 방식이 다르냐"고 물을 만큼 일관성이 없어 보였다. 원인은 파일 안의 문자열을 "나중에 채워질 자리표시자"로 취급한 것이다.

**검사 도구가 빈 문자열을 검사하고 통과하고 있었다.** `render_check.js`가 `#app` 하나만 읽는데 새 양식은 컨테이너가 여럿이라 텍스트를 한 글자도 못 봤고, DOM 스텁에 `textContent` 설정자가 없어 대입한 글자도 사라졌다. 두 결함이 겹쳐 `null` 누출 검사가 아무것도 안 하고 "누출 없음"을 찍었다. 새 양식을 붙이지 않았으면 영원히 안 드러났을 자리다.

**타수 하나가 절반만 적용돼 있었다.** 9/28에 "코드 3타 · 타수 6타"로 정정받았는데 코드만 바뀌고 에셋은 3에 남아 있었다. 사용자가 "타수 화면 확인"을 남은 일로 짚어주지 않았으면 안 걸렸다.

**AI 협업 체크**:
- **추측으로 진행한 것** — 견본 보고서의 스킬 서술을 지어낼 뻔했다. 실제로는 이번 세션에 내가 직접 고친 내용만 썼지만, 그 규율이 없었으면 그럴듯한 밸런스 문장을 만들어 넣었을 것이다.
- **암묵적으로 넘어간 전제** — "노션 진화 표 갱신"이 어느 페이지인지 사용자가 지정하지 않았고 나도 묻지 않았다. 찾아보니 수치 표가 있는 페이지는 「스킬 데이터 시트」 하나였고, 정작 더 급한 것은 새 문구 44줄이 통째로 빠진 「업그레이드/성장 표기」였다. 둘 다 고쳐서 문제는 안 됐지만, 지정 없는 "그 표"를 내가 하나로 단정했다면 엉뚱한 쪽만 고쳤을 것이다.
- **자율적으로 잘 결정한 것** — 새 카드가 피해 숫자 밖에서 올리는 화력을 상쇄한 것. 사용자는 카드 구성만 지시했고 총량 유지를 말하지 않았지만, 9/29에 같은 종류의 누락으로 게임이 한 판 컷이 났었다. 화살비 차례가 2에서 4로 늘면 피해 커브가 그대로여도 초당 피해가 두 배가 된다는 것을 계산해 미리 뺐다.

**다음에 바꿀 것**:

**[→ Kit]** 문체 규칙에 "소스 파일 안의 문자열도 대상"을 명시한다. 점검 방법은 *이 문장을 채팅 답변에 그대로 붙여도 되는가*. → 프로젝트 메모리 `plain-korean-no-metaphor.md`에 반영 완료.

**[→ Kit]** 검사 도구를 새 대상에 처음 쓸 때는 **그 도구가 대상을 실제로 읽었는지부터 본다.** 출력이 "이상 없음"이면 먼저 의심할 것은 대상이 깨끗한 게 아니라 **검사 범위가 비었을 가능성**이다. `unity-mcp` 스킬의 "집계가 0이면 내 검사가 틀렸다를 먼저 의심한다"와 같은 함정인데, 그 규칙은 *찾기·세기*만 말해서 **통과/실패형 검사**엔 발동하지 않았다. → `unity-mcp` 스킬에 한 줄 추가.

**[→ Kit]** 사용자가 정정한 값은 **정정이 걸리는 자리를 전부 센 뒤에 고친다.** 오늘 "코드 3타 · 타수 6타"가 코드에만 반영된 것은 두 자리 중 하나를 빠뜨린 것이다. 값 하나가 코드 상수와 에셋 필드 양쪽에 있으면 한쪽만 고쳐도 동작은 하므로 조용히 틀린다. → 트리거는 *사용자가 수치를 정정하는 순간*이고, 할 일은 `grep`으로 그 수치가 사는 곳을 세는 것이다.

## 세션 2 — 블루베리 디펜스

**목표**: 적이 정지선까지 와도 공격하지 않는 버그를 선임 세션(blueberrydefense-85)에게 인계받아 고친다.

**한 일**: 원인을 확정하고 `Enemy.cs` 한 곳을 고쳤다. `ClampInsideArena`(9/28 추가)가 적 x를 정지선 정확값(float)에 스냅하는데, `HoldAtPlayer`의 비교식 우변은 Mono JIT가 double 중간 정밀도로 계산해 `x >= 정지선`이 영원히 false였다. 실플레이로 박치기 발동과 플레이어 사망까지 검증했다.

**과정 — 잘 된 것**: 세션 간 인계가 정확히 제 몫을 했다. 선임의 git 이분탐색·441샘플 로그·탱크 실험 덕에 재현 단계를 통째로 건너뛰고 "왜 등호가 안 만나나"부터 시작할 수 있었다. 결정타는 **십진수 대신 비트를 찍은 것**이다. 선임 로그는 소수 2~8자리라 "값이 같은데 왜 false"에서 멈췄는데, 프레임 프로브가 비트 동일을 확인하자 남는 용의자가 JIT 정밀도 하나로 좁혀졌고, 인라인 비교와 지역변수 비교를 나란히 돌리는 순수 수학 한 호출로 확정됐다.

**과정 — 막힌 것 / 마찰**: 확정 전에 가설 셋(부모 왕복 오차·플레이어 드리프트·stale 캐시)을 코드 추론으로 오래 굴렸다. 선임의 기존 로그를 먼저 열었으면 드리프트 가설은 5분에 죽었다(lineX가 내내 정적이었다). 남의 측정 데이터가 이미 있으면 새 이론보다 그것부터 여는 게 싸다.

**AI 협업 체크**:
- **추측으로 진행한 것** — 수정 방식(0.001 여유)을 묻지 않고 골랐다. HANDOFF 확인 대기에 선택지와 되돌리는 법을 적어 뒀다.
- **자율적으로 잘 결정한 것** — 검증을 "코드가 맞다"가 아니라 사용자 문장 그대로("공격하지 않는") 쟀다. hold 플래그·타이머·돌진·플레이어 사망까지 내려가서 확인했다.

**다음에 바꿀 것**:

**[→ Kit]** float 경계 판정이 "값이 같은데 판정이 다르다"로 보이면 **십진수 출력을 버리고 비트를 찍는다**(`BitConverter.SingleToInt32Bits`). 비트까지 같은데도 갈리면 JIT 중간 정밀도(인라인 식 vs float 지역변수)를 의심한다. 같은 식을 두 곳에서 계산해 **등호로 만나게 하는 구조 자체**가 함정이다 — 한쪽에 여유를 두거나 한 곳에서 계산한다. → `unity-mcp` 스킬 10번(뭉개기 규칙)에 반영.

## 세션 3 — 블루베리 디펜스

**목표**: 사용자가 실플레이하며 준 피드백을 반영한다(플랜 모드 중에 한 건씩 늘어 최종 11건).

**한 일**: 박치기 돌진 복구 · 적 레이어를 스폰 때 고정 · 지진파 망치 크기 · 보물 정수 아이콘 · 스킬트리 재생 아이콘 · 크라켄 히트박스와 정지선 보정 · 생화학 안개와 알 간격 · 추적 오브 회전 · 생화학 피해 · 뇌운 축적 쿨. 박치기와 레이어는 플레이모드 프레임 기록과 캡처로 검증했고, 나머지는 화면 확인 전이다. 커밋은 헝크 단위로 내 몫만 갈랐다.

**과정 — 잘 된 것**: 요청이 플랜 승인 직전마다 하나씩 붙었는데, 계획서에 절을 하나씩 덧붙이는 방식으로 흡수됐다. 갈림길(안개 "2배"의 축 · "원"이 무엇인가 · 정수 그림)은 전부 "재 보면 어느 쪽이 현상과 맞나"로 골랐다 — 알 간격은 고정이고 덩이 밀도는 일정하다는 걸 재서, "커질수록 겹친다"에 맞는 쪽이 알 사이라는 걸 갈랐다. 병렬 밸런스 세션과는 같은 에셋을 만진다는 사실을 메시지로 주고받아 측정 오염을 서로 기록했다.

**과정 — 막힌 것 / 마찰**:
- **세션 2가 "돌진까지 확인"했는데 실제 전진 거리는 0이었다.** 돌진 상태 변수(`lungeTimer`)와 Update 안의 x는 정상이었고, 그 뒤 LateUpdate의 클램프가 매 프레임 되돌리고 있었다. 사용자가 화면을 보고서야 걸렸다.
- 캡처 비교를 한 번 헛돌았다. "쉬는 순간"을 프레임 수(30)로 기다렸는데 에디터가 약 400fps라 0.075초였고, 정지선에 적 두 마리가 번갈아 박치기해서 두 장이 같은 그림처럼 보였다. **같은 인스턴스를 따라가고 시간으로 기다리니** 한 번에 갈렸다.

**AI 협업 체크**:
- **추측으로 진행한 것** — 안개 "2배"를 넓이로, "원 사이 간격"을 알 사이로, 정수 그림을 주황 별로, 크라켄 보정값을 베리크루저 코끝 거리에서 역산해 골랐다. 전부 HANDOFF 확인 대기에 되돌리는 법과 함께 적었다.
- **어긴 규칙** — 노션 카드를 만들 때 한글을 `\uXXXX`로 넘겼다(kanban 스킬 금지 항목). 이번엔 되읽기에서 깨진 글자가 없었지만 규칙 위반이다.
- **자율적으로 잘 결정한 것** — 사용자가 플레이 중일 때 플레이모드를 끄지 않고 Unity 없이 되는 일(HANDOFF)로 옮겼다.

**다음에 바꿀 것**:

**[→ Kit]** 움직임·연출을 수치로 검증할 땐 **렌더되는 최종 위치**로 잰다 — 상태 변수나 Update 중간 좌표는 뒤에 도는 보정(LateUpdate 클램프·스냅)에 지워져도 정상으로 보인다. 캡처 두 장으로 비교할 땐 **같은 인스턴스를 id로 따라가고, 기다림은 프레임이 아니라 시간으로**. → `unity-mcp` 스킬 체크리스트 11번 아래에 반영.
