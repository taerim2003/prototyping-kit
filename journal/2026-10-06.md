## 세션 1 — BlueberryDefense (일시정지 창 수치 · 망치 · DX12 크래시)

**목표**: 일시정지 창의 패시브 수치가 스킬트리 몫까지 합쳐 나오는 것을 고친다. 도중에 파인애플 망치 사라짐과 엔딩 크래시가 들어왔다.

**한 일**: 일시정지 창이 이번 판에서 패시브가 올린 몫만 보이게 고쳤다(4종). 파인애플 `AttackBody` 상태의 Write Defaults를 꺼서 망치가 유지되게 했다. 10/5 빌드의 엔딩 크래시를 Player.log와 덤프 두 개로 분석했고, 태리미 결정으로 Windows 빌드를 DX11로 고정했다. 옆 세션이 뽑은 10/6 빌드가 Direct3D 11로 도는 것까지 확인됐다. 앞의 두 건은 화면 확인을 못 했다.

**과정 — 잘 된 것**:
- 크래시 스택을 Unity 설치 폴더의 PDB로 풀고, 미니덤프를 직접 파싱해 예외 코드와 레지스터를 읽었다. 디버거가 없는 PC에서도 "포인터 자리에 작은 정수가 들어 있었다"까지 갔다.
- 두 번째 덤프를 받자 죽은 명령과 값의 모양이 똑같아서, 같은 결함인지가 한 번에 갈렸다.
- 빌드 중인 옆 세션에 읽기 전용 확인을 요청했고, 값이 어긋났을 때 고치지 말고 알려 달라고 한 것이 맞았다. 두 조회가 다른 답을 냈고 결국 빌드 결과물의 로그로 판정했다.

**과정 — 막힌 것 / 마찰**:
- Unity MCP가 작업 초반에 끊겨서 이후 전부 화면 확인 없이 진행했다. 프로젝트 설정도 파일만 고쳤다.
- `PlayerSkills.cs` · `PlayerPassives.cs`에 다른 세션의 미커밋 변경이 수십 덩어리 섞여 있어서, 내 변경만 떼어 커밋하지 못했다. 미커밋 파일이 128개까지 쌓여 있었다.
- Python이 없어서 덤프 파서를 Node로 다시 썼다.

**AI 협업 체크**:
- 추측으로 진행한 것: 크레딧에서 죽었다는 말을 듣고 폰트 아틀라스 업로드를 원인 후보로 올렸고, 외부 사례를 찾은 뒤 그쪽으로 기울어 보고했다. 10/1 덤프와 로그를 받고 나서야 씬 로드 직후에도 같은 자리에서 죽었다는 것이 나왔다. 표본 하나로 방아쇠를 지목한 것이다.
- 사용자가 바로잡은 것: "게임이 멈췄다"는 말을 메인 스레드 정지로 받아 답했는데 실제로는 강제 종료였다. 힘 레벨업 15% 건은 태리미가 직접 획득 카드 수치였다고 정정했다. DX11 고정은 "저번에 하라고 했을 텐데"라고 했는데, 카드에는 시험 후 결정으로 남아 있었다.
- 규칙을 어긴 것: 노션에 한글을 유니코드 이스케이프로 보냈다. kanban 스킬이 금지한 방식이다. 되읽기에서 깨진 글자는 없었다.
- 잘 결정한 것: DX12/DX11 값이 어긋난 상태에서 그래픽 API 설정 호출을 막아 둔 것. 확인 창이 뜨는지 모르는 호출이었다.

**다음에 바꿀 것**: 세션이 `.cs`를 고쳤으면 그 세션 안에서 자기 몫을 커밋한다. 같은 파일에 여러 세션의 미커밋 변경이 쌓이면 나중에는 떼어 낼 수 없다. 규칙으로 넣을지는 태리미와 정한다.

**메모**: Steam 상점 출시일이 안 뜨던 것은 Steamworks에서 저장만 하고 게시를 안 누른 것이었다. 공개 `appdetails` API로 상점 쪽 값을 직접 조회하니 캐시 문제가 아닌 것이 바로 갈렸다.

## 세션 2 — BlueberryDefense (손 밸런스 조정)

**목표**: 태리미가 플레이하면서 불러 주는 밸런스 조정을 그 자리에서 반영한다.

**한 일**: 치명타 배율, 패시브 진화체 레벨업 카드 8종, 전탄발사 쿨타임·지속·기계 연출, 화살 2차 두 갈래, 스킬트리 쿨타임 노드와 후반 20노드 가격, 20~25층 물량, 스포너의 프레임당 1마리 제한을 고쳤다. 컴파일 검사와 트리 가격 검사기는 통과했다. 게임 화면으로 확인한 것은 하나도 없다.

**과정 — 잘 된 것**:
- 요청 문장과 현재 값이 어긋날 때 값을 먼저 쟀다. "암살 초기 확률을 20%로 줄이자"(실제 15%), "10회마다 미사일 추가"(실제 20회), "피해 상승값이 있으면 빼고"(이미 없음) 세 건이 그 자리에서 드러났다.
- "왜 지속시간과 쿨타임이 같지?"를 받고 원인 두 개(트리 쿨감 40%, 1차 지속 카드 상속)를 수식으로 갈라 보여준 뒤에야 태리미가 손잡이를 골랐다. 처음 낸 안(지속 절반)은 증상만 줄이는 것이었다.
- 패시브 진화 카드를 조사하다가 문구 문제가 아닌 것 세 건(상한에 막혀 버려지는 카드, 6레벨이 무효인 카드, 서로 상쇄되는 두 축)을 찾았다.

**과정 — 막힌 것 / 마찰**:
- 세션 내내 Unity MCP가 붙지 않았다. 첫 응답에서 한 줄로 알리고 넘어갔고, 태리미가 끝에 "너도 연결 안 돼 있어?"라고 물었다. 30건 가까운 변경이 전부 미확인으로 쌓였다.
- 20~25층 물량을 올리면서 간격을 같은 비율로 줄였는데, 스포너가 프레임당 1마리만 내보내고 간격을 프레임 배수로 올림한다는 것을 적용한 뒤에 알았다. 줄인 간격의 절반은 아무 효과가 없었다.
- 계획서의 합계(66,824)를 손으로 더해 틀렸다(실제 66,424). 스크립트 출력에서 드러났다.
- 계획 승인이 다섯 번 거절됐다. 태리미가 계획을 읽는 동안 다음 생각을 덧붙이는 흐름이었고, 거절 사유가 따로 오지 않아 매번 같은 요약을 다시 썼다.
- 세션 1과 같은 작업 폴더를 동시에 고쳤다. 컴파일 검사가 그쪽의 변경(`JuicyButton`의 새 멤버) 때문에 실패해 원인을 가르는 데 세 번을 돌렸다. 오프라인 검사는 별도 어셈블리를 옛 DLL로 참조한다.

**AI 협업 체크**:
- 추측으로 진행한 것: "우주선"을 비행선으로, "후반 20노드"를 가격 상위 20개로, "게릴라 3배"를 처음엔 횟수 증가로 읽었다. 마지막 건은 태리미가 "동시에 여러 부대가 나오면 되잖아"로 바로잡았다. 예고마다 정문 스폰이 멈춘다는 부작용을 보고서에 적고도 그 설계를 그대로 따랐다.
- 사용자가 지적한 것: 전탄발사 가동률의 원인을 쿨감 노드로 지목한 것은 태리미였다. 그 수치를 표에 적어 놓고도 스킬 쪽 값만 만지는 안을 냈다.
- 규칙을 어긴 것: 노션 카드를 만들 때 한글이 유니코드 이스케이프로 나갔다. 세션 1과 같은 위반이다. 되읽기에서 깨진 글자는 없었다.
- 잘 결정한 것: 스포너를 고치면 1~19층도 빨라진다는 것을 전수 조사로 재서 보고했다. 가격을 올릴 때 기존 세이브의 보유 정수가 음수가 되는 문제를 9/28 사례에서 떠올려 보정을 같이 넣었다.

**다음에 바꿀 것**:
- **[→ Kit]** 시간 값을 프레임 시간 근처로 내리기 전에 그 값을 읽는 코드에 하한·올림이 있는지 본다. 프로젝트 `CLAUDE.md` §1과 키트 `templates/CLAUDE.md`에 넣었다.
- 세션 시작에 Unity MCP가 안 붙어 있으면 변경을 쌓기 전에 "이 세션은 화면 확인을 못 한다"를 먼저 말하고 재시작을 권한다.
- 합계·배수는 손으로 계산해 문서에 적지 않고 스크립트 출력에서 옮긴다.

**메모**: 오늘 변경은 전부 `HANDOFF.md`의 확인 대기와 칸반 카드 「10/6 손 밸런스 조정」에 미확인으로 남아 있다.

## 세션 3 — BlueberryDefense (스토어 스크린샷 · 출시 빌드) — 10/6 시작, 10/7 종료

**목표**: 스토어용 영어 스크린샷 30장. 이어서 들어온 요청(폭발 이펙트, 맵 훈장, 뇌운 축적, 군집체, 출시 준비)을 처리하고 출시 빌드를 뽑는다.

**한 일**: 스크린샷 32장을 저장소 밖 폴더에 찍었습니다. 핵 폭발을 화면에 맞추고 숫자 뒤로 내렸습니다. 맵 카드에 난이도 훈장을 달았습니다. 뇌운 축적이 4스택에서 멈추는 원인을 실측으로 찾아 스택 구조를 바꿨습니다. 군집체를 맵 가운데로 옮겼습니다. 스플래시 끔, 중복 실행 방지, 중국어 63칸, 세이브 재시도를 넣고 빌드를 세 번 뽑아 노션에 올렸습니다.

**과정 — 잘 된 것**:
- 플레이모드에 들어가기 전에 에디터 세이브를 백업했고, 작업이 끝날 때마다 바이트 단위로 대조했습니다. 선택 캐릭터가 바뀐 것을 이 대조로 잡았습니다.
- 뇌운 축적은 코드를 읽어서는 버그가 안 보였습니다. 레벨별로 상한·시전 간격·실제 최대 스택을 재서 표로 놓으니 원인(유지 시간 ÷ 시전 간격)이 바로 갈렸습니다. 수정 뒤 같은 측정을 다시 돌려 4/6/8/10을 확인했습니다.
- 훈장이 안 고른 카드에서 안 켜지는 것은 값 검사로는 통과했고 캡처에서 걸렸습니다. `JuicyButton` 주석에 해법(`SetDimBaseColor`)이 적혀 있었습니다.
- 군집체는 "맵 가운데"를 그대로 따르되, 기본 휘두르기가 여전히 3.95 모자란다는 측정값을 같이 보고했습니다. 사용자가 그 숫자를 보고 정중앙으로 확정했습니다.

**과정 — 막힌 것 / 마찰**:
- "DX11로 되어 있다"를 `ProjectSettings.asset`과 빌드 로그 줄만 보고 답했습니다. 빌드 프로필이 프로젝트 설정을 덮는다는 사실이 HANDOFF에 적혀 있었는데 읽지 않았습니다. `/clear` 직후 바로 작업 지시가 와서 `brief`를 건너뛴 탓입니다. 나중에 창으로 띄운 `Player.log`를 찾아 정정했습니다.
- 같은 에디터에서 다른 작업이 진행 중인데 플레이모드를 여러 번 드나들고 씬을 저장했습니다. `git status`에 내가 안 고친 파일이 뜬 뒤에야 알았습니다.
- `/build`가 한 번 큐에 넣은 빌드를 연달아 다시 돌렸습니다(5회, 2회). 첫 `DONE`을 보고 zip을 만들었다가 출력 폴더가 지워진 순간과 겹쳐 빈 zip이 나왔습니다. 원인은 못 찾았습니다.
- 플레이모드 자동화의 기록을 `AppDomain` 데이터에 담았다가, 스크립트가 스스로 플레이를 끄면서 도메인이 내려가 측정 결과를 한 번 통째로 잃었습니다. 파일로 바꿔 다시 돌렸습니다.
- 노션 카드를 만들 때 한글을 유니코드 이스케이프로 보냈습니다. `kanban` 스킬이 금지한 방식이고, 10/7 다른 세션 일기에도 같은 기록이 있습니다. 되읽기에서 깨진 글자는 없었습니다.
- Steam 아이콘 규격을 문서로 확인하지 못한 채 기억으로 답했습니다. 그 사실은 답에 적었습니다.

**AI 협업 체크**:
- 추측으로 진행한 것: 훈장 1·2·3을 쉬움·보통·어려움으로 읽었습니다. 훈장 크기를 1.5배로 키웠다가 위치를 옮기면서 원본 크기로 되돌렸습니다. 뇌운 축적은 유지 시간을 늘리는 대신 구조를 바꿨고, 세지는 정도를 수치로 보고했습니다.
- 사용자가 지적해 준 것: 처음 전투 스크린샷에 적이 없다는 것. 폭발 이펙트가 화면을 벗어나고 숫자를 가린다는 것. 독수리가 아니라 폭발이 주인공이라는 것.
- 잘 결정한 것: 출시 점검 요청에서 최근 실행 로그를 열어 세이브 저장 실패 1건을 찾았습니다. 사용자가 지목하지 않은 축이었습니다.

**다음에 바꿀 것**:
- 빌드 완료 판정을 "`DONE` 한 줄"이 아니라 "`DONE` 뒤 40초간 새 줄 없음"으로 바꿉니다. BlueberryDefense `build` 스킬 2단계에 넣었습니다(프로젝트 스킬이라 키트에는 해당 없음).
- 플레이모드 자동화의 결과는 처음부터 파일에 씁니다. 플레이를 끄는 스크립트는 `AppDomain` 데이터를 못 남깁니다.
- 세션 첫 턴이 작업 지시여도 HANDOFF의 「현재 상태」 절은 읽고 시작합니다.

**메모**: 이번 커밋에는 제 변경만 넣었습니다. 다른 작업의 미커밋 파일(`HomingMissile.cs`, `Orb.cs`, `ScalingTable.cs`, 도전과제 아이콘 등)은 그대로 뒀습니다.
