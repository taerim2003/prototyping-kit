**과정 — 막힌 것 / 마찰**:
- **🔴 기존 기능 중복 구현.** ESC 상세 패널을 새로 만들었는데, 이미 `PauseMenu.cs`가 ESC 일시정지+요약을 자동 부트스트랩으로 돌고 있었다. **ESC 충돌** + 사용자가 보던 건 기존(레벨업치 미표시) 패널. 착수 전 `grep ESC|Escape|Pause`를 안 한 탓. 새 스크립트·씬 오브젝트 만들었다가 통째로 되돌리고 기존 것에 통합.
- **🔴 플레이모드 중 씬 저장 불가.** Title 레이아웃 5건을 수정·저장하려다 "cannot be used during play mode"로 막힘 — 사용자가 테스트 중이었다. 플레이 종료 요청→도메인리로드로 인스턴스ID 바뀜→5건 재적용→저장. 왕복 1회.
- 피드백 해석: "스킬 정보 다 표시"를 처음엔 진화 티어 나열로만 받아, 사용자가 "레벨업 증가분까지 다"라고 재지시. (마침 중복 발견과 겹쳐 한 번에 정리됨)

**AI 협업 체크**:
- 추측으로 진행? — **ESC 기능 기존재 여부를 확인 안 하고** 새로 구현한 게 최대 실수. "게임 중 ESC 패널" 요청 = 기존 ESC 핸들러부터 grep했어야.
- 암묵 전제? — 체력회복 maxLevel 1 전환 시 4%를 그대로 둘지(단일 개방엔 낮을 수 있음) 확인 없이 진행. 사용자가 수용했으나 명시 안 함.
- 자율 결정 잘한 것 — 2스테이지 레이스 원인 규명, 해금노드 범위를 AskUserQuestion으로 확정(이름에 '해금'만), 런타임 생성으로 플레이모드 우회. 재현할 것.

**다음에 바꿀 것**:
- **[→ Kit] 신규 UI/입력 기능 착수 전 기존 핸들러 grep 의무화**: "ESC/일시정지/패널/토글" 류는 반드시 `grep`으로 기존 구현 확인 후 만들 것(중복·입력충돌 방지).
- 세션 초에 **플레이모드 여부부터 확인**(scene-save 필요한 작업이면 사용자에게 종료 요청 선행). 플레이 중엔 씬 편집 미루기.
- maxLevel↔per-level 값 동반 변경 시 최종 단일값을 한 줄로 사용자 확인.

## 세션 2 — 리팩토링 계획 수립 + Phase 0(정찰·문서화) 실행

**목표**: 앞으로 만들 피쳐(신규 캐릭터·캐릭터 선택·신규 맵·맵 선택 + 유니티 내 밸런스 편집 툴)를 위한 리팩토링 계획 수립. 합의되면 첫 단계 착수.

**한 일**:
- 코드/씬을 정찰해 "이 게임에서 캐릭터=스킬셋, 맵=환경+스테이지테이블"임을 규정하고, 기존 `MetaBonuses`/`MetaRunApplier` 패턴을 확장하는 6-Phase 로드맵을 HANDOFF.md에 확정.
- 두 개의 갈림길(캐릭터/맵이 "얼마나 다른가")을 AskUserQuestion으로 못박음 → 신규스킬 캐릭터 / 로스터·기믹 맵(둘 다 중간 티어).
- 밸런스 편집 요구를 같은 SO 백본에 흡수(별도 트랙 아님)로 통합, Tier A/B 원칙 정립.
- **Phase 0 실행**(코드변경 0): MCP로 Title·SampleScene 정찰 → `SCENE_MAP.md`·`BALANCE_MAP.md` 신규 작성, CLAUDE.md §7 루틴 갱신.

**과정 — 잘 된 것**:
- 코딩 착수 전에 **결정 갈림길을 AskUserQuestion으로 먼저 확정**한 게 계획 규모(과설계 여부)를 좌우하는 핵심이었다. "캐릭터가 얼마나 다른가"를 안 물었으면 PlayerSkills 플러그인화 같은 speculative 작업으로 샜을 것.
- "씬 문서 만들까?"라는 사용자 질문을 **단순 문서가 아니라 정찰(recon)로 재프레이밍** — SCENE_MAP 작성 자체가 이후 Phase를 검증·de-risk하는 단계임을 짚고, 뜨거운 컨텍스트일 때 지금 하자고 판단.
- 계획을 그대로 따르지 않고 **RunConfig를 Phase 0→1로 미룸**(읽는 쪽 없는 코드는 speculative, §2). 문서를 맹종 안 하고 원칙으로 교정.
- 정찰이 **실제 발견**을 냄: BGM 시스템 부재(스왑이 아니라 신규추가), Player 단일 오브젝트, RunBootstrap 부착점=GameManager. 감이 아니라 씬 사실 기반.

**과정 — 막힌 것 / 마찰**:
- 큰 마찰 없음. MCP 씬 정찰은 `scene-get-data`(깊이 지정) + 오브젝트별 `gameobject-find`(컴포넌트) 조합으로 매끄러웠다. 다만 `assets-find`를 필터 없이 부르니 전체 덤프가 튀어나와 1회 낭비 — 애초에 필요 없던 호출.
- 세션이 계획→질문→재검토→실행으로 길어졌으나, 각 단계가 다음 결정을 좁혀서 헛돌지는 않음.

**AI 협업 체크**:
- 추측으로 진행? — 계획 단계에서 갈림길을 추측 안 하고 물은 게 정답. 씬 사실도 추측 대신 MCP로 확인(StageTable 위치·BGM 유무).
- 암묵 전제? — 없음. RunConfig 이동 같은 계획 수정도 침묵으로 넘기지 않고 사용자에게 근거와 함께 고지.
- 자율 결정 잘한 것 — 씬 문서=정찰 재프레이밍, Tier A/B 경계(값=데이터·흐름=코드) 확립, Phase 순서를 결합 얕은 맵부터. 재현할 것.

**다음에 바꿀 것**:
- **[→ Kit] MCP 씬 정찰 레시피**: `scene-list-opened`→`scene-get-data`(depth 2~3, includeData=false)→핵심 매니저만 `gameobject-find(includeComponents)`. `assets-find`는 반드시 필터와 함께. 이 순서를 씬 있는 프로젝트 온보딩에 명시.
- **[→ Kit] SCENE_MAP.md를 Kit 표준 산출물로**: MCP로 씬 만지는 프로젝트는 ARCHITECTURE(코드지도)와 별도로 씬지도를 두고, "MCP 쿼리로 찾는 건 안 적음" 원칙으로 rot 방지.

**메모**:
- 다음 세션 착수점 = Phase 1(맵/적 데이터). HANDOFF 로드맵 + SCENE_MAP + BALANCE_MAP 3종이 콜드스타트 비용을 낮춰줌.
- 정찰 중 에디터 활성 씬이 Title→SampleScene으로 바뀜(둘 다 저장, 무해).
- Phase 1·3(데이터 추출)은 각각 한 세션 통으로 잡을 것. 매 Phase 끝에 사용자 플레이테스트 게이트.
