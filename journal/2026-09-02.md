## 세션 1 — 블루베리 디펜스 (세션 54)

**목표**: 칸반 「09/01~09/04」 카드 밑의 체크리스트 3건을 처리하고, 이어서 태리미가 순서대로 던지는 8/27 QA 결정 항목들을 구현.

**한 일**: 체크리스트 3건(컬렉션 아이콘 dim 반전 · 연계 아이콘 순서 · 파인애플 망치 정렬)과
**8/27 빌드 QA 결정 5건 전부**(산탄 총구 화염 · 관통산탄 전탄발사 · 일시정지 레이아웃 · 데미지 숫자 큐 · 산탄 구조 개편)를 끝냈다.
곁가지로 관통 무한, 종류 태그(공격/버프/유틸) 제거, 산탄 설명문 정정까지. 커밋은 세션 끝에 1건.
검증은 전부 플레이모드 실측 + 캡처로 했고, `.cs`는 매번 오프라인 Roslyn으로 먼저 컴파일했다.

**과정 — 잘 된 것**:
- **오프라인 컴파일 검증이 세션의 뼈대였다.** 고칠 때마다 Bee의 rsp + Unity 번들 Roslyn으로 돌려서
  에디터에 들어가기 전에 문법 오류를 다 걸렀다. 도메인 리로드를 강요하지 않아 왕복이 확 줄었다.
  중간에 에디터 어셈블리(`Assembly-CSharp-Editor`)도 같은 방식으로 돌려 `LocHarvest` 참조가 안 깨졌는지 봤다.
- **방향이 갈리는 걸 그림으로 끝냈다.** 불꽃이 "위를 향한다 / 오른쪽을 향해야 한다"로 말이 어긋났을 때,
  PNG를 0·90·180·270도로 렌더한 4컷을 만들어 **어느 쪽이 왼쪽을 보는 그림인지**를 한 번에 확정했다.
  이어서 게임 화면에서 A(z=0)/B(z=180) 두 안을 한 장에 담아 찍으니 태리미가 "z=0" 한마디로 끝냈다.
- **판을 알파로 재서 레이아웃을 잡았다.** 일시정지 `Columns`가 1080×880 판에서 **379×183만** 쓰고 있던 걸
  실측으로 찾았다(겹침의 진짜 원인). 판 그림의 불투명 실루엣을 재서 좌우/위/아래 여백을 정했다.
- **말과 사실이 어긋난 자리에서 멈춘 것.** "오른쪽을 향해야 해"와 "알은 왼쪽으로 난다"가 모순인 걸 알아차리고
  밀어붙이지 않고 두 안을 나란히 찍었다. 그대로 갔으면 180도 반대로 만들었다.

**과정 — 막힌 것 / 마찰**:
- 🔴 **`assets-refresh`를 빠뜨리고 플레이모드에 들어가 한 바퀴를 통째로 날렸다.** 일시정지 패널의 항목 높이가
  안 바뀌길래 TMP 문제로 파고들었는데, 실제로는 방금 고친 `PauseMenu.cs`가 **에디터에서 컴파일도 안 된 상태**였다.
  오프라인 컴파일이 통과했으니 "코드는 맞다"고 믿은 게 함정 — 그건 **에디터가 그 코드를 들고 있다는 뜻이 아니다.**
- 🔴 **겹침 원인을 두 번 오진했다.** "TMP가 폭 확정 전에 높이를 계산한다"고 단정하고 `ForceMeshUpdate`까지 넣었는데,
  실제 원인은 **내용이 칸보다 컸던 것**(필요 609px vs 칸 495px)이었다. **값을 재기 전에 그럴듯한 원인을 먼저 골랐다.**
- **플레이모드 왕복이 너무 많았다.** 타이틀→캐릭터→맵→배틀을 이번 세션에만 7~8번 밟았고 매번 4~5 호출을 썼다.
- **입력 검증에서 `wasPressedThisFrame` / `isPressed` 차이로 한 바퀴.** `InputSystem.Update()`를 직접 부르면
  `wasPressedThisFrame`이 그 안에서 소진돼 게임 루프가 못 본다(W는 `isPressed`라 걸렸고 ESC는 안 걸렸다).
- **레벨업·보물 모달이 캡처와 입력을 계속 방해했다.** "W가 안 먹는다"를 코드에서 찾다가
  레벨업 창이 떠서 입력이 막혀 있던 걸 뒤늦게 발견한 게 두 번.

**AI 협업 체크** *(코드 버그 말고 과정 레벨로)*:
- 🔴 **유저가 명시했어야 했는데 넘어갈 뻔한 전제 — 아니, 내가 안 읽은 것**: 「데미지 숫자 쌓기」를
  **HANDOFF의 네 글자 라벨만 보고 지어냈다.** 원본 회의록에는 해법("메이플식 — 새 숫자는 아래, 기존은 위로 밀림")이
  이미 적혀 있었는데 안 열어보고, **정반대 방향**(숫자를 합치기 / 이 스킬만 숫자 끄기) 두 안을 내밀었다.
  태리미가 *"네가 어떻게 이해했는지 설명해봐"* 라고 물어서야 원본을 열었다.
- **물어봤어야 하는데 추측으로 간 것**: "1루트 버프로 바꿔"를 route index 0(집중 산탄)으로 읽고 진행했다.
  근거는 댔지만(그 루트가 원래 버프 강화 코드를 들고 있었다) 틀리면 정반대가 되는 자리였다 — 한 줄 물었어도 됐다.
- **잘 결정한 것 (재현하고 싶은 것)**: 관통 산탄의 **설명문이 거짓말이 되는 걸 스스로 찾아 고친 것.**
  버프를 빼고 나니 "5초 동안 공격 횟수 증가"와 "열기가 더 오래 남는다"가 둘 다 사실이 아니게 됐다 —
  요청에 없었지만 안 고치면 화면이 거짓을 말한다.

**다음에 바꿀 것**:
- **[→ Kit] `.cs`를 고친 뒤 `EnterPlaymode` 전에 `assets-refresh`를 부른다.** 오프라인 컴파일 통과는
  에디터가 그 코드를 들고 있다는 뜻이 아니다. 증상이 **"내 수정이 반영 안 된 화면"** 으로 나와 게임 로직 버그처럼 보인다.
  → `unity-mcp` 스킬의 "재컴파일을 기대하는 모든 작업의 선행" 절 옆에 붙였다.
- **[→ Kit] HANDOFF·카드의 *요약 라벨*을 근거로 설명하거나 선택지를 만들지 말 것 — 원본을 먼저 연다.**
  기존 규칙("문서에 적힌 건 낡는다")은 *적힌 내용*을 의심하라고만 해서, **적혀 있지도 않은 것을 내가 채워 넣는 경우**엔
  발동을 안 했다. → 프로젝트 `CLAUDE.md` §7과 키트 `templates/CLAUDE.md` 둘 다에 넣었다.
- 플레이모드 검증이 여러 건이면 **한 번 들어가서 다 끝낸다.** 오늘은 코드 수정 → 나가기 → refresh → 재진입을 반복했다.

**메모**: 노션 `API-update-page-markdown`이 체크박스 줄 매칭에 계속 실패한다(줄 전체를 정확히 넣어도 `No matches found`).
카드 본문 체크는 여전히 손으로 해야 한다 — 상태(status) 변경은 `API-patch-page`로 잘 된다.

## 세션 2 — 블루베리 디펜스 (세션 55)

**목표**: Unity CLI를 우리 프로젝트에 적용할 수 있는지 검토 — 기존 Unity-MCP 대체 가능성을 시간·정확도·토큰 관점에서.

**한 일**: 게임 코드는 한 줄도 안 건드렸다. Unity CLI의 실체를 확인하고(1st-party, `com.unity.pipeline`이 에디터 안에
로컬 HTTP 서버를 띄우는 구조), **38개 세션 트랜스크립트를 직접 세서** 우리 MCP 사용 프로필을 실측했다 —
`script-execute`가 2003건 중 1580건(79%)이고, 보낸 C# 코드가 Unity 관련 토큰의 74%(576k). 결론은
**"지금 프로토타입은 MCP 유지, 다음 프로토타입 세션 0에서 CLI 우선"**. 킷 `templates/CLAUDE.md` §6과
`SESSION_ZERO.md`, 프로젝트 `HANDOFF.md`에 각각 반영(사본이 아니라 실체 1곳 + 포인터 2곳).

**과정 — 잘 된 것**: **"값을 먼저 재 본다"가 결론을 두 번 뒤집었다.** ① 트랜스크립트를 세기 전엔 "타입 툴 40개를
갈아타야 한다"고 봤는데, 실제로는 우리가 쓰는 게 사실상 `eval` 하나였다. ② 토큰도 마찬가지 — 실측 없이 갔으면
"CLI가 토큰을 아낀다"는 홍보 문구를 그대로 옮겼을 것이다. 재보니 비용의 대부분이 **내가 보내는 C# 코드**라
전송 계층을 바꿔도 안 줄어든다. 로컬 확인(설치 여부·훅·스킬 크기)을 웹 조사와 같은 턴에 병렬로 돌린 것도 빨랐다.

**과정 — 막힌 것 / 마찰**:
- 유니티 공식 문서가 WebFetch에 네비게이션만 주고 본문을 안 내줘서 3번 헛돌았다. 명령 전수 목록은 결국
  커뮤니티가 만든 스킬 문서(GitHub raw)가 가장 정확했다. **공식 문서가 SPA면 raw 마크다운을 먼저 찾는 게 빠르다.**
- `python`이 Windows Store stub이라 첫 계측이 빈손으로 돌아왔다(출력이 `Python` 한 줄). node로 갈아타서 해결.

**AI 협업 체크**:
- **축을 의심하지 않고 성실히 쟀다 — 이번 세션 최대 실수.** 사용자가 준 세 축(시간·정확도·토큰)으로 재니
  대부분 무승부가 나왔고, 나는 그걸 "우수한 점이 거의 없다"로 요약했다. 사용자가 *"정말 우수한 점이 거의 없는거야?"*
  라고 되물어서야 플레이모드 제어·Undo 묶기·헤드리스 컴파일이 서드파티 MCP엔 **아예 없는 기능**임을 확인했다.
  **축이 모자랐던 것이지 CLI가 별로였던 게 아니다.**
- **추측으로 진행한 것**: "Unity CLI"가 뭘 가리키는지 안 묻고 웹에서 찾았다. 이번엔 맞았지만 사내 스크립트를
  가리켰다면 통째로 헛일이었다. 다만 찾는 비용이 묻는 비용보다 쌌고, 찾자마자 **실체부터 보고**한 순서는 맞았다.
- **잘 결정한 것 둘**: ① 사용자 표현("MCP를 대체")을 그대로 받지 않고 **구조가 포함 관계임을 먼저 정정**한 것.
  ② 킷에 규칙을 넣을 때 **"속도·토큰은 근거가 아니다"를 명시적으로 적어둔 것** — 틀린 근거로 다시 갈아타자는
  말이 나오는 걸 막는다.

**다음에 바꿀 것**:
- **[→ Kit] 사용자가 평가 축을 지정해 주면, 재기 전에 "이 축들로 안 잡히는 게 있나"를 한 번 본다.**
  지정된 축만 성실히 재면 결론이 "차이 없음"으로 나오고, 그게 **"가치 없음"으로 잘못 요약된다.**
  트리거 자명 — *사용자가 "A·B·C 관점에서 봐줘"라고 축을 나열하는 순간.*
  → 프로젝트 `CLAUDE.md` §1과 키트 `templates/CLAUDE.md` 둘 다에 넣었다.

**메모**: Unity CLI·`com.unity.pipeline`은 둘 다 experimental(0.4.0-exp.1)이다. 다음 프로토타입 착수 때
`unity --help`와 `unity command`로 능력을 **직접 다시 확인**해야 한다 — 이번에 정리한 목록은 그때 낡아 있을 것이다.
