# 2026-07-11

## 세션 1 — 블루베리 디펜스

**목표**: 지난 세션에 만든 오브 설치기/개큰 회오리/체인 라이트닝을 밸런스 튜닝하고, 사용자가 보고한 "게임하다 멈춘다" 버그를 잡는다.

**한 일**: 프리징 버그의 진짜 원인(모달 패널 이중 오픈으로 인한 `Time.timeScale` 참조 카운트 불일치)을 찾아 수정. 체인 라이트닝을 회전시킨 낙뢰 VFX에서 `LineRenderer` 기반 실제 연결선으로 교체(2차 수정까지 감). 사운드 겹침으로 인한 렉을 클립 디바운스로 완화. 오브 설치기/개큰 회오리 밸런스 다수 조정. 에디터 치트창(`CheatWindow`)과 데이터 기반 선택지 시스템(SO 2종)을 새로 구축.

**과정 — 잘 된 것**: 사용자가 "회오리 업글했더니 또 멈추던데"처럼 재현 조건을 구체적으로 짚어줄 때마다 원인 특정이 훨씬 빨랐음 — 프리징 버그는 이 한 마디 덕분에 "여러 회오리가 동시에 한 적을 오버킬 → 사망 처리 중복 → 모달 이중 오픈"이라는 사슬을 바로 추적할 수 있었다. 이전 세션에 정착한 "정적 RectTransform/코드 흐름 분석으로 검증, play 모드에 의존하지 않기" 습관이 이번에도 유효했음 — 프리징 버그도, 체인 라이트닝의 근본 원인(에셋 자체가 세로 낙뢰 모양이라 회전으로는 해결 불가)도 코드/로그만 보고 특정함.

**과정 — 막힌 것 / 마찰**: 데이터 기반 선택지 시스템(ScriptableObject 에셋 추가 방식)을 제안했는데, 사용자가 "너무 어렵다"며 즉시 거부하고 에디터 창(치트 UI) 방식을 요청함 — 두 방식 다 "코드 안 건드리고 콘텐츠 추가"라는 같은 목적이지만, 실제로 원하는 건 "에셋을 만들고 필드를 채우는" 워크플로가 아니라 "버튼 누르면 바로 적용되는" 워크플로였다. 처음부터 "그 에디터"가 뭘 가리키는지, "선택지"가 뭘 가리키는지 물어봤음에도 첫 제안이 빗나갔던 걸 보면, 질문에서 구체적 UI 형태(에셋 vs 버튼)까지 확인했어야 했다.

**AI 협업 체크**:
- AI가 물어봤어야 하는데 추측으로 진행한 게 있었나? → 있음. "그 에디터에서 선택지 추가하는 기능"을 확인 질문(AskUserQuestion)으로 물었지만 선택지가 "LevelUp/Evolution 중 어느 쪽이냐"에만 집중했고, "에셋 기반이냐 버튼 기반이냐"라는 더 근본적인 UX 형태는 안 물어보고 바로 SO 방식으로 구현했다가 헛수고가 됨.
- 유저가 명시했어야 했는데 암묵적으로 넘어간 전제가 있었나? → 초기 요청 "그 에디터에서 사용할 수 있는... 기능"이라는 표현 자체가 이미 "에디터 창"을 가리키고 있었는데, 텍스트만 보고 "에디터(Unity)에서 편집 가능한 데이터"로 잘못 해석함.
- AI가 자율적으로 잘 결정한 게 있었나? → 체인 라이트닝 2차 수정 때, 사용자는 "여전히 세로로 떨어진다"고만 말했는데 AI가 스스로 "체인 대상에게도 기존 낙뢰 VFX가 중복 재생되고 있다"는 원인을 코드 추적으로 찾아내고, 재질문 없이 바로 수정(억제 플래그 추가 + 빔 강조)까지 진행한 것은 재현하고 싶은 흐름.

**다음에 바꿀 것**: "에디터에서 쓸 수 있는 기능 만들어줘" 류의 애매한 요청은 AskUserQuestion에서 반드시 "에셋/데이터 편집 방식 vs 즉시 적용되는 버튼(치트) 방식" 두 옵션을 명시적으로 제시할 것. **[→ Kit]** — CLAUDE.md에 "에디터 확장 기능 요청 시 SO 데이터 편집과 EditorWindow 버튼 방식을 구분해서 먼저 물어볼 것" 항목 추가 고려.

**메모**: 프리징 버그가 "회오리 업그레이드 후"라는 특정 조건에서만 재현된 건 회오리가 유일하게 스킬 하나로 동시에 여러 인스턴스(분열 소환)를 만드는 스킬이기 때문 — 다른 스킬은 이 오버킬-중복 사망처리 경로를 못 밟는 구조였다. 비슷한 "동시다발 히트" 스킬을 새로 추가할 때 이 케이스를 염두에 둘 것.

## 세션 2 — 블루베리 디펜스 (사운드 디버깅, 미해결로 종료)

**목표**: 체인 라이트닝 가시성 개선 + 기본공격에서 낙뢰가 안 나가는 느낌 검증 → 이후 사용자 요청으로 사운드 전반(발사음/사망음/각종 임팩트음) 볼륨·재생 안정성 조정으로 확장.

**한 일**: `Enemy.TakeDamage`에서 낙뢰 발동 확률 판정이 사망 체크보다 뒤에 있어서 킬샷(특히 기본공격)이 낙뢰를 아예 못 굴리던 진짜 버그 발견·수정. 이후 사운드 쪽으로 넘어가서: 사망음이 "안 들린다" → 원인 추적하다 `m_audioClip`/`m_Resource` 필드 불일치(직렬화 방식 차이로 `AudioSource.clip`이 null 판정되는 버그)를 발견해 전수조사, 클립 교체 여러 차례, `ObjectPool`을 안 거치는 사운드에 쓰로틀링 추가, `playOnAwake`와 수동 재생 로직이 충돌해 소리를 자기 자신이 Stop() 시키는 구조적 버그 발견·수정, 발사음 전용 재생 시스템(`SfxPlayer.cs`, 상시 AudioSource + PlayOneShot) 신규 도입까지 갔지만 **마지막에 사용자가 "쏘는 소리가 갑자기 커지고 가끔 씹힌다"고 재보고 — 검증 못 하고 "그냥 세션 마무리해"로 종료.**

**과정 — 잘 된 것**: 사운드 버그 5~6개를 실제로 코드/직렬화 레벨에서 진짜 원인까지 추적해서 고쳤다는 점은 성과. 특히 `m_audioClip` vs `m_Resource` 직렬화 불일치, `playOnAwake`와 `ObjectPool` 수동 재생의 충돌은 겉으로 "가끔 안 들림"으로만 보이는 걸 근본 원인까지 파고든 사례. `AskUserQuestion`으로 "어떻게 처리할까" 물어보고 진행한 부분(임팩트음 쓰로틀링 적용 여부)은 방향을 맞게 잡은 지점.

**과정 — 막힌 것 / 마찰**: **가장 큰 문제는 매번 "이번엔 고쳤다"고 보고했는데 사용자가 다음 턴마다 또 다른 증상(또는 같은 증상의 재발)을 보고하는 패턴이 5차례 넘게 반복된 것.** 원인은 한 번에 한 증상만 보고 국소 수정 → 다음 증상 보고 → 또 국소 수정을 반복하면서, **볼륨 값을 담당하는 곳이 개별 프리팹 m_Volume / fireSfxVolume / castSfxVolume / SfxPlayer.MasterVolume으로 계속 늘어나기만 하고 정리가 안 됐다.** 사용자가 "코드 완전 다시 새로 짜"라고 할 정도로 신뢰를 잃은 시점까지 왔는데, 돌이켜보면 2~3번째 "아직도 이상하다" 보고를 받은 시점에 **국소 패치를 멈추고 전체 사운드 재생 경로(어떤 스크립트가 언제 무엇을 부르는지, 볼륨이 어디서 곱해지는지)를 표로 한 번 정리하고 사용자에게 공유했어야** 했다. 매번 "이번엔 확실합니다" 톤으로 보고한 것도 반복될수록 신뢰를 깎아먹었을 가능성이 큼.

**AI 협업 체크**:
- AI가 물어봤어야 하는데 추측으로 진행한 게 있었나? → 있음. 볼륨을 몇 차례나 "이 정도면 되겠지"로 임의 수치 조정했는데, 사용자에게 "지금 소리가 어느 정도로 크게/작게 들리는지 1~10 정도로 알려달라" 같은 구체적 기준을 한 번도 안 물어보고 계속 추측성 배율(1.3배, 1.5배 등)로 밀어붙였다. 정량적 피드백 없이 반복 조정한 게 시간 낭비의 큰 축.
- 유저가 명시했어야 했는데 암묵적으로 넘어간 전제가 있었나? → "씹힌다"는 표현이 이번 세션에서 최소 3가지 다른 의미(발사체 Destroy로 인한 끊김 / Stop()에 의한 묵음 / 겹쳐 재생으로 인한 클리핑 추정)로 쓰였는데, 매번 이전과 같은 증상이라고 넘겨짚고 이전에 고친 부분만 손댐. "씹힌다"가 정확히 어떻게 들리는지(짧게 끊기는지/아예 안 나는지/지지직거리는지) 구체적으로 되물었어야 했다.
- AI가 자율적으로 잘 결정한 게 있었나? → `m_audioClip`/`m_Resource` 불일치나 `playOnAwake` 충돌처럼, 사용자가 "왜 안 들리냐"고만 물었을 때 직렬화 YAML까지 직접 읽어 근본 원인을 찾아낸 점은 재현하고 싶은 디버깅 태도.

**다음에 바꿀 것**: 같은 영역(이번엔 사운드)에서 "고쳤다" → "아직도 문제"가 **2번 이상 반복되면, 세 번째 시도부터는 국소 수정을 멈추고 그 영역 전체의 데이터/제어 흐름을 표나 다이어그램으로 한 번 정리해서 공유한 뒤 재설계 여부를 먼저 상의할 것.** **[→ Kit]** — CLAUDE.md에 "같은 증상 카테고리가 2회 이상 재발하면 국소 패치 대신 전체 구조 재검토를 먼저 제안" 원칙 추가 고려. 볼륨처럼 여러 곳에 값이 분산되기 쉬운 항목은 처음부터 단일 소스(예: 마스터 볼륨 하나 + 카테고리별 배율 하나)로 설계했어야 함.

**메모**: HANDOFF.md에 이번 세션 마지막 상태와 다음 세션이 참고할 구체적 의심 지점(쓰로틀 윈도우, 볼륨 이중 곱셈)을 남겨둠 — 다음 세션은 반드시 이 문서부터 읽고 재설계 여부부터 사용자와 상의할 것.
