**목표**: "호밍 「초강력 슈퍼 로켓」은 어떤 조합으로도 못 얻는다"는 문구가 사실인지 확인하고 원인 설명.

**한 일**: 사실로 확인(액티브 5개 필요 > 슬롯 4). 원인은 세션61에서 위임받아 채운 열쇠표가 "어울림"만 봤기 때문.
사용자가 규칙을 새로 정함 — 열쇠는 1차 조건을 이어받는다 · 전용 조건이면 전용 열쇠 · 순환 금지 · 겹침 없음.

**과정 — 잘 된 것**:

- 노션과 코드가 어긋난 칸(오브 R1)을 `last_edited_by` + `get-self`로 "사용자 편집이 코드보다 나중"임을 갈라 냈다.
- 계획 모드에서 사용자가 중간에 규칙을 세 번 덧붙였는데(전용 예외 · 순환 · 겹침), 매번 표 전체를 다시 계산해 계획 파일에 반영했다.

**과정 — 막힌 것 / 마찰**:

## 세션 3 — BlueberryDefense (후반 렉 최적화)

**목표**: "후반에 렉 많이 걸린다 — 스킬 이펙트 풀링 안 돼 있나?" 원인 분석과 해결.

**한 일**: 렉 보고가 세 번 왔고 원인이 매번 달랐다. ① 타격 파편 3,872개 동시(상한 → 사용자가 2000으로) ② 미니 회오리 수명 없음 → 적 없을 때 화면 밖에 463개 누적(수명 4초) ③ 표적 없는 호밍 미사일 260~516발이 매 프레임 `FindObjectsByType<Enemy>`(1회 0.76ms) → 스크립트 197ms. ③은 `Enemy.Active` 활성 목록으로 게임 코드 23곳 교체해 해결, 같은 판 조건에서 스테이지 24까지 실시간 866초+ → 25까지 118초. 그 외 호밍 꼬리 재질 누수·화살/호밍 풀링·데미지 숫자 메시 재생성·지연 반납 무할당. 사용자 지시로 호밍 성장 8→5% · 「더 많은 폭격」 10→20회(노션·TSV·번역 표까지).

**과정 — 잘 된 것**:
- 봇 세션이 Unity를 쥔 동안 **읽기 전용 `script-execute` + `Profiler.Recorder`**(켜는 호출과 읽는 호출을 나눔)로 실전 판을 방해 없이 쟀다. "종류별 활성 MonoBehaviour 개수 전수"를 첫 조회로 고정하니 ②③은 한 호출에 범인이 보였다.
- 봇 세션과 cross-session 메시지로 파일 편집·컴파일·플레이모드 사용을 매번 조율했고, 봇 쪽이 만든 `BotRuns/yield`로 즉시 비키게 한 뒤 컴파일 → 재개가 5분 안에 끝났다.
- 번역 표 적재 메뉴가 `SaveAssets`로 **남의 미저장 에셋(빌드 프로필)까지 저장**한다는 걸 실행 전 코드로 보고, 해당 키만 넣고 `SaveAssetIfDirty`로 두 표만 저장했다(`git diff` 파일당 1줄).

**과정 — 막힌 것 / 마찰**:
- 🔴 스크린샷(적 몇 마리)을 보고 `FindObjectsByType`을 **"적이 적으니 싸다"며 순위를 내렸다.** 실제 비용은 활성 적 수가 아니라 풀에 쌓인 비활성 오브젝트 수에 비례했고, 그게 ②③의 공통 원인이었다. 계획엔 34곳 전수 교체가 있었는데 "계측 후 조건부"로 미뤄서 **같은 병을 세 번 따로 고쳤다.** 1회 호출 시간을 먼저 쟀으면 첫 턴에 끝났다.
- 계획의 0단계(수정 전 기준선)를 봇 세션 때문에 못 해서 "전후 비교"가 서로 다른 판끼리의 비교가 됐다. 마지막 ③에서야 같은 판 재시작(resumeFrom)으로 제대로 된 A/B가 나왔다.
- 노션 호출 인자를 또 유니코드 이스케이프로 보냈다(오늘 세 세션 연속). 되읽기로 깨짐 0 확인.

**AI 협업 체크**:
- 추측으로 진행: 파편 상한 800(사용자가 2000으로 바꿈 — "에디터가 빌드보다 느리다"), 미니 회오리 **화면 밖 소멸**(사용자는 수명을 골랐다 — 내 안은 뒤집힘), 미니 수명 길이 4초(확인받음).
- 유저가 명시 안 한 전제: 렉 판단 기준이 에디터 체감인지 빌드인지. 사용자가 먼저 "빌드는 나을 것"이라고 말해줘서 상한을 넉넉히 잡았다.
- 잘 결정한 것: 호밍 발 수 질문에 공식만 말하지 않고 봇 `runs.jsonl`에서 판당 시전 수(우주 어려움 540~660)를 뽑아 "판 끝 120발"로 답해 사용자가 바로 너프를 결정할 수 있었다.

**다음에 바꿀 것**: 성능 가설 순위를 매기기 전에 **후보 호출 1회 시간을 먼저 잰다**(CLAUDE.md §1 "실측 한 번이 더 싸다"와 같은 규칙이라 키트 반영 없음 — 어긴 기록으로만 남김). 같은 종류 원인을 한 곳에서 확인하면 계획에 적어둔 전수 교체를 미루지 않는다.

## 세션 4 — BlueberryDefense (밸런스 루프 무인 실행 · Unity 멈춤)

**목표**: `/loop /balance-loop 5 11:00` — 봇 플레이테스트로 기준선을 재고, 이터레이션마다 손잡이 하나를 밀어 재측정.

**한 일**: 기준선(정주행 42판 + 난이도 30판) 측정 → 1회차 해변 콩콩이 밀도 −0.15 → 판정 불가 → 2회차 우주 비행선 밀도 ×2.2 적용 → **측정 3/63판에서 Unity 메인 스레드가 굳어 루프 중단(06:39)**. 사용자가 7시간 뒤 화면을 보여줘서 클리어 화면에서 멈춘 것을 확인하고, `Editor.log`로 예외 없음·`Update` 미작동을 갈라냈다. 상한 없던 `BotTree` 루프에 상한을 넣고, 단계 이름을 세션 폴더 `trace.log`에 동기로 남기게 했다. 보고서 아티팩트는 판정마다 갱신.

**과정 — 잘 된 것**:
- 첫 틱에서 **기본 규모로는 하룻밤에 이터레이션 1회도 못 돈다**는 것을 과거 세션의 판당 실시간으로 계산해, 규모를 줄이고 그 근거·되돌릴 곳을 이터레이션 파일에 적고 시작했다. 결과적으로 기준선+2회차까지 갔다.
- 손대지 않은 맵의 D가 같이 ±0.1~0.18 움직이는 것을 보고 **노이즈 폭을 데이터에서 읽어** 판정을 "불가"로 두고 표본을 2배로 올렸다. 가설이 맞았다고 보고하지 않은 것이 이 세션의 핵심 판단.
- G4가 0으로 나왔을 때 **같은 기준선의 정주행이 4/4 클리어**라는 모순을 보고 판정을 보류했다. 다음 측정에서 0.667로 확인 — 보류가 맞았다.
- 에셋을 디스크로 고친 뒤 **에디터가 그 값을 들고 있는지** `SerializedObject`로 되읽어 확인했다(두 번 다). 안 했으면 옛 값으로 측정하고 판정까지 했을 것이다.

**과정 — 막힌 것 / 마찰**:
- 멈춤을 "Unity가 죽었다"로 보고했는데, 실제로는 **판 클리어 화면에서 봇만 멈춘** 것이었다. 프로세스 생존·파일 mtime·컴파일 흔적까지 봤지만 **`Editor.log` 꼬리를 안 봤다** — 그게 "예외 없음 = 동기 루프에 갇힘"을 바로 말해주는 줄이었다. 사용자가 화면을 보여줘서야 열었다.
- 봇에 워치독이 있는데 **그 워치독이 `Update()`에 있어서** 메인 스레드가 굳으면 같이 죽는다. 무인 실행의 감시장치를 같은 스레드에 두면 감시가 안 된다.
- 이터레이션 하나가 1.5시간이라 5회 마감이 처음부터 불가능했다. 규모를 줄이는 대신 **정주행을 빼서** G1·G3 추이를 끊었다 — 우선순위 최하위라 감수했지만, 이런 교환은 루프를 걸기 전에 사용자가 알고 있어야 한다.

**AI 협업 체크**:
- 추측으로 진행: 측정 규모 축소 · 2회차부터 정주행 생략 · 판정 불가인 1회차 변경을 유지 · 2회차 손잡이를 비행선(구성)으로 고른 것. 전부 HANDOFF 확인 대기에 적었다.
- 유저가 명시 안 한 전제: 하룻밤 예산 안에서 **판정 정확도와 이터레이션 수 중 무엇을 살릴지**. 나는 "판정할 수 없는 측정은 이터레이션이 아니다"로 읽고 표본을 늘렸다.

## 세션 5 — BlueberryDefense (후반 렉 2차 — 코드가 지목한 범인이 틀렸다)

**목표**: 사용자가 스크린샷과 함께 보고한 후반 렉(스테이지 20/25, Lv.127)의 원인을 찾고 고친다.

**한 일**: 실측 세 가지로 원인을 특정했다 — ① 봇 260런의 `gameTime`/`realTime` 집계로 후반 처리량이 초중반의 1/3임을 확인 ② 스테이지 20 이상 58런을 스킬 사용 여부로 갈라 **호밍(3.64배속 vs 미사용 6.06배속)** 을 단독 범인으로 지목 ③ 플레이 중 읽기 전용 프로브로 렌더링 무죄(drawCall 197)·`GC.Collect()` 764ms 블로킹 확인. 이후 `HomingMissile` 재타겟을 매 프레임 → 0.15초 + 위상 분산으로 바꾸고, 정렬 키를 사전 계산하고, `Enemy.Active` foreach 박싱을 4곳에서 없앴다(총 5파일).

**과정 — 잘 된 것**:
- **이미 쌓여 있던 봇 로그가 답을 갖고 있었다.** `runs.jsonl`에 런별 `gameTime`/`realTime`이 있어서 "어느 스킬이 렉을 만드는가"를 한 번의 집계로 갈랐다. 이 축은 밸런싱용으로 쌓은 것인데 성능 진단에 그대로 쓰였다.
- **옛 알고리즘을 벤치마크 안에 재현해 A/B로 돌린 것.** 비용 비교(505→91us)와 **결과 동치(불일치 0/200)** 를 한 호출에 얻었다. 밸런스 중립임을 이걸로 증명했다. 대조군(rank를 1 어긋내면 200/200 불일치)까지 같이 넣어 검사가 살아 있음을 보였다.
- 에디트모드 + `HideFlags.HideAndDontSave`로 가짜 적 200마리를 만들어 재고 치웠다 — 씬은 `IsDirty: false`로 유지됐다.

**과정 — 막힌 것 / 마찰**:
- 🔴 **코드 정독이 지목한 1순위가 데이터에서는 노이즈였다.** 서브에이전트 둘이 각각 "독수리 투하가 적 1마리당 미니 회오리를 1개씩 만든다(`PlayerSkills.cs:2276`)"를 최대 후보로 올렸는데, 실측은 EagleDrop +0.27 · Whirlwind −0.27로 **유의하지 않았다.** 코드는 *비용이 큰 것*은 찾아주지만 *실제로 자주 도는 것*은 못 찾는다. 에이전트 둘에 33만 토큰을 쓴 것보다 `runs.jsonl` 집계 한 번이 정확했다.
- 계획에 적은 "전체 정렬 → 상위 k개 부분 선택"이 **구현하려니 더 느린 안**이었다(`k = TargetRank % N`이 최대 89까지 간다). 계획서에 쓰기 전에 k의 범위를 안 따진 것. 구현 중에 정정했다.
- `Profiler.GetMonoUsedSizeLong()` 1.09GB를 처음엔 게임 누수로 읽을 뻔했다. **에디터 프로세스 전체값**이라 MonoScript 9401개·콘솔·MCP·내가 실행한 진단 어셈블리가 다 들어 있다. 빌드로 재야 갈린다.

**AI 협업 체크**:
- 추측으로 진행: VFX 반납 지연 단축·`DamageNumber` 상한·미사일 수 상한을 **안 묻고 보류**했다(병목 근거가 없거나 밸런스 손잡이라서). HANDOFF 확인 대기에 적었다.
- 유저가 명시 안 한 전제: **에디터 플레이인지 빌드인지.** 스크린샷으로 에디터라 판단했는데, 빌드였다면 GC보다 순수 CPU 비중이 커진다. 물었어야 했다기보다 **첫 보고에 그 가정을 적었어야** 했다.
- 잘 결정한 것: 코드 근거 둘이 한목소리로 지목한 범인을 **데이터로 뒤집은 것**. 그리고 계획의 한 항목이 틀렸음을 구현 중에 발견하고 사용자에게 정정을 먼저 말한 것.

**다음에 바꿀 것**: **[→ Kit]** **병목을 코드로 지목하기 전에 이미 쌓인 로그·측정 데이터에 그 축이 들어 있는지 먼저 본다.** 트리거 자명 — *"이게 느린 원인이다"를 말하려는 순간.* 코드 정독은 "한 번에 비싼 것"을 찾고 로그는 "실제로 자주 도는 것"을 찾는데, 후반 렉의 범인은 늘 후자다. 반영: 프로젝트 `CLAUDE.md` §1 + 키트 `templates/CLAUDE.md` 같은 자리.

**메모**: 판 전체 효과는 아직 미측정 — 봇 재측정이 남았다(목표: `Homing` 런 3.64 → 5.5배속). `BotPilot.cs`·`analyze.js`·`report.html`은 **병렬 봇 루프 세션의 작업물**이라 커밋에서 뺐다.
