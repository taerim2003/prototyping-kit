## 세션 1 — BlueberryDefense (2차 진화 열쇠)

**목표**: "호밍 「초강력 슈퍼 로켓」은 어떤 조합으로도 못 얻는다"는 문구가 사실인지 확인하고 원인 설명.

**한 일**: 사실로 확인(액티브 5개 필요 > 슬롯 4). 원인은 세션61에서 위임받아 채운 열쇠표가 "어울림"만 봤기 때문.
사용자가 규칙을 새로 정함 — 열쇠는 1차 조건을 이어받는다 · 전용 조건이면 전용 열쇠 · 순환 금지 · 겹침 없음.
`EvolutionRoutes`의 14칸 + 오브 R1 조건(노션 빨간 글씨 반영)을 고치고, 실제 코드를 컴파일해 22칸 × 캐릭터 3 감사(전부 0, 옛 표 대조군은 위반 12·순환 7)를 돌렸다. 노션 표·칸반 카드 갱신.

**과정 — 잘 된 것**:
- Unity가 봇 플레이 중이라 에디터 컴파일이 막혔는데, 오프라인 컴파일(메모리의 rsp + 번들 Roslyn)로 **실제 `EvolutionRoutes.cs`를 콘솔 프로그램에 넣어** 감사했다. 표를 옮겨 적지 않아 사본 오차가 없고, HEAD 버전을 같은 프로그램에 넣어 대조군이 공짜로 나왔다.
- 노션과 코드가 어긋난 칸(오브 R1)을 `last_edited_by` + `get-self`로 "사용자 편집이 코드보다 나중"임을 갈라 냈다.
- 계획 모드에서 사용자가 중간에 규칙을 세 번 덧붙였는데(전용 예외 · 순환 · 겹침), 매번 표 전체를 다시 계산해 계획 파일에 반영했다.

**과정 — 막힌 것 / 마찰**:
- 세션61 HANDOFF의 "KeyAudit 슬롯 초과 0" 주장이 틀렸었다. 스크립트는 스크래치패드에 있어 사라졌고 **주장만 남아** 사실처럼 인용될 뻔했다. 이번 감사 스크립트도 스크래치패드에만 있다.
- 새로 제안한 산탄 R0 대안의 이유("순환 차단")가 사용자의 후속 지정(독수리 R0 → 메카 버스터)으로 절반 무효가 됐는데, 감사 대조군을 돌리고서야 알았다.
- 노션 호출 인자가 한글 대신 유니코드 이스케이프로 나갔다(kanban 스킬 금지 사항). 이번엔 되읽기에서 깨짐 0이었다.

**AI 협업 체크**:
- 추측으로 진행: 오브 R1을 노션 쪽으로 따를지(사용자 확인 "빨간 글씨면 노션이 맞을걸"), 열쇠 루트의 테마 선택 몇 칸(오브 R0은 사용자가 "잘 어울린다"로 확정).
- 유저가 암묵적으로 갖고 있던 전제: "2차 열쇠는 1차 조건을 이어받는다". 세션61의 위임("어울릴 만한 걸로")에는 안 적혀 있었다 — 위임받은 설계가 사용자 머릿속 구조 규칙과 어긋날 수 있다.
- 잘 결정한 것: 두 스킬 맞물림만 묻는 요청에 **길이 무관 순환**까지 재서 3자 순환을 찾아낸 것.

**다음에 바꿀 것**: 감사 스크립트를 남길지 사용자에게 한 줄로 넘김(프로젝트 `Tools/`에 둘지). 키트 반영 없음 — 대조군·사본 금지·문서 주장 의심은 이미 규칙에 있다.

## 세션 2 — BlueberryDefense (md 문서 정리 · 노션 대조)

**목표**: HANDOFF를 비롯한 md 문서를 중요한 것만 남기게 정리하고, 노션과 다른 곳을 모아 보고.

**한 일**: HANDOFF 369→112줄(병렬 세션이 확인 대기 88건을 먼저 지움 → 나머지 세션별 서술을 주제별 사실로 합침). ARCHITECTURE의 사라진 심볼 9곳 정정 + HANDOFF에 있던 코드 규칙 4개 이관. SCENE_MAP은 씬 YAML을 파싱해 실제 계층으로 재작성(SampleScene→Battle, 진화창 4칸 등). GDD 진화 절을 코드 기준으로 재작성하고 루트 표는 노션 데이터 시트 포인터로. CLAUDE.md 날짜 사례 8곳 삭제. 노션이 낡은 곳 5건은 고치지 않고 칸반 카드로.

**과정 — 잘 된 것**:
- 씬 구조를 MCP 대신 `.unity` YAML 파서(스크래치패드 `scenetree.js`)로 뽑아 봇 세션의 Unity 사용과 안 부딪혔다. 문서의 "3×3 잔재"·"캐릭터 1종" 같은 낡은 서술이 한 번에 드러났다.
- 병렬 세션과 cross-session 메시지로 HANDOFF 충돌을 피했다 — 상대 `/wrap` 커밋이 끝난 알림을 받고 최신본에서 시작.
- 줄 삭제 스크립트를 dry-run으로 먼저 돌려 블록 수(8)·줄 수(14)를 grep과 맞춘 뒤 적용.

**과정 — 막힌 것 / 마찰**:
- 계획을 세우는 사이 병렬 세션이 HANDOFF를 크게 바꿔, 계획의 절반(확인 대기 압축)이 무효가 됐다. 공유 문서는 계획이 아니라 실행 직전 상태가 기준이다.
- "노션 vs md" 대조로 시작했지만 실제로는 노션끼리도 갱신 속도가 달랐다(데이터 시트는 9/18 최신, 기획서는 9/8). 결국 문서 5곳 × 코드의 대조가 됐다.
- 노션 카드 생성 인자를 또 유니코드 이스케이프로 보냈다(오늘 두 세션 연속). 되읽기 단계에서 깨짐 0 확인 — 규범은 안 먹히고 되읽기 단계가 막고 있다.

**AI 협업 체크**:
- 추측으로 진행: "중요한 내용"의 기준(완료·사본·규칙성 서술 삭제), GDD 루트 표를 지우고 포인터로 바꾼 것, 노션 목록을 HANDOFF 대신 칸반 카드로 둔 것 — 앞 둘은 HANDOFF 확인 대기에 적음.
- 유저가 명시 안 한 전제: CLAUDE.md도 정리 대상인가. 규칙은 안 건드리고 사례만 지우는 선으로 좁혔다.
- 잘 결정한 것: HANDOFF에서 뺀 코드 규칙을 CLAUDE.md가 아니라 ARCHITECTURE로 옮겨 CLAUDE.md를 더 불리지 않은 것.

**다음에 바꿀 것**: `scenetree.js`를 프로젝트 `.claude/scripts/`에 둘지 사용자 판단(SCENE_MAP 갱신 비용이 거의 0이 된다). 키트 반영 없음 — 사본 금지·실행 직전 재읽기·쓰기 후 되읽기는 이미 규칙에 있다.

## 세션 3 — BlueberryDefense (후반 렉 최적화)

**목표**: "후반에 렉 많이 걸린다 — 스킬 이펙트 풀링 안 돼 있나?" 원인 분석과 해결.

**한 일**: 렉 보고가 세 번 왔고 원인이 매번 달랐다. ① 타격 파편 3,872개 동시(상한 → 사용자가 2000으로) ② 미니 회오리 수명 없음 → 적 없을 때 화면 밖에 463개 누적(수명 4초) ③ 표적 없는 호밍 미사일 260~516발이 매 프레임 `FindObjectsByType<Enemy>`(1회 0.76ms) → 스크립트 197ms. ③은 `Enemy.Active` 활성 목록으로 게임 코드 23곳 교체해 해결, 같은 판 조건에서 스테이지 24까지 실시간 866초+ → 25까지 118초. 그 외 호밍 꼬리 재질 누수·화살/호밍 풀링·데미지 숫자 메시 재생성·지연 반납 무할당. 사용자 지시로 호밍 성장 8→5% · 「더 많은 폭격」 10→20회(노션·TSV·번역 표까지).

**과정 — 잘 된 것**:
- 봇 세션이 Unity를 쥔 동안 **읽기 전용 `script-execute` + `Profiler.Recorder`**(켜는 호출과 읽는 호출을 나눔)로 실전 판을 방해 없이 쟀다. "종류별 활성 MonoBehaviour 개수 전수"를 첫 조회로 고정하니 ②③은 한 호출에 범인이 보였다.
- 봇 세션과 cross-session 메시지로 파일 편집·컴파일·플레이모드 사용을 매번 조율했고, 봇 쪽이 만든 `BotRuns/yield`로 즉시 비키게 한 뒤 컴파일 → 재개가 5분 안에 끝났다.
- 번역 표 적재 메뉴가 `SaveAssets`로 **남의 미저장 에셋(빌드 프로필)까지 저장**한다는 걸 실행 전 코드로 보고, 해당 키만 넣고 `SaveAssetIfDirty`로 두 표만 저장했다(`git diff` 파일당 1줄).

**과정 — 막힌 것 / 마찰**:
- 🔴 스크린샷(적 몇 마리)을 보고 `FindObjectsByType`을 **"적이 적으니 싸다"며 순위를 내렸다.** 실제 비용은 활성 적 수가 아니라 풀에 쌓인 비활성 오브젝트 수에 비례했고, 그게 ②③의 공통 원인이었다. 계획엔 34곳 전수 교체가 있었는데 "계측 후 조건부"로 미뤄서 **같은 병을 세 번 따로 고쳤다.** 1회 호출 시간을 먼저 쟀으면 첫 턴에 끝났다.
- 계획의 0단계(수정 전 기준선)를 봇 세션 때문에 못 해서 "전후 비교"가 서로 다른 판끼리의 비교가 됐다. 마지막 ③에서야 같은 판 재시작(resumeFrom)으로 제대로 된 A/B가 나왔다.
- 노션 호출 인자를 또 유니코드 이스케이프로 보냈다(오늘 세 세션 연속). 되읽기로 깨짐 0 확인.

**AI 협업 체크**:
- 추측으로 진행: 파편 상한 800(사용자가 2000으로 바꿈 — "에디터가 빌드보다 느리다"), 미니 회오리 **화면 밖 소멸**(사용자는 수명을 골랐다 — 내 안은 뒤집힘), 미니 수명 길이 4초(확인받음).
- 유저가 명시 안 한 전제: 렉 판단 기준이 에디터 체감인지 빌드인지. 사용자가 먼저 "빌드는 나을 것"이라고 말해줘서 상한을 넉넉히 잡았다.
- 잘 결정한 것: 호밍 발 수 질문에 공식만 말하지 않고 봇 `runs.jsonl`에서 판당 시전 수(우주 어려움 540~660)를 뽑아 "판 끝 120발"로 답해 사용자가 바로 너프를 결정할 수 있었다.

**다음에 바꿀 것**: 성능 가설 순위를 매기기 전에 **후보 호출 1회 시간을 먼저 잰다**(CLAUDE.md §1 "실측 한 번이 더 싸다"와 같은 규칙이라 키트 반영 없음 — 어긴 기록으로만 남김). 같은 종류 원인을 한 곳에서 확인하면 계획에 적어둔 전수 교체를 미루지 않는다.
