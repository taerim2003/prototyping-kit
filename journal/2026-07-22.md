# 2026-07-22

## 세션 1 — 블루베리 디펜스: 게임 루프 구축 (스킬트리 재편 + 해금 게이팅 + 승천)

**목표**: "처음엔 못 깨다가 → 스킬 해금·강화 → 깬다"는 루프를 실제로 성립시키기. 오늘 할일 목록(스킬 종류 표시 / 승천 / 스킬트리 재편)을 구체화부터 시작.

**한 일**:
- **재편**: 자원 3개(정수·결정·가루)+아웃게임 전역레벨을 **정수 하나로** 통일, 되돌리기(환불·리스펙·빌드셋 5슬롯) 전부 제거, 노드 3종 재정의 후 요청받아 4종(특수해금)까지 확장. 비용을 노드별 직접입력 → **등급(tier)제**로 바꿔 상수 2개로 전체 밸런싱되게.
- **루프 연결**: `SkillUnlock` 노드가 인게임 레벨업 카드 풀을 게이팅(캐릭터 풀 ∩ 트리 해금). 트리에 해금 노드 없는 스킬은 게이팅 안 하는 폴백을 넣어 재설계 중에도 게임이 안 잠기게.
- **승천**: 프레스티지 리셋이 아니라 **슬더식 난이도 등급**으로 확정 → `AscensionTable` SO(1~3, 체력·이속·데미지만) + `EnemySpawner` 적용 + 클리어 시 다음 등급 해금 + 맵 선택 화면 `◀ 승천 N ▶` UI.
- 사용자가 트리를 다 짠 뒤 **코드 대조 감사**: 효과 매핑이 없는 노드 4개·리롤 로직 꼬임·표시 필드 불일치를 찾아 보고하고, 승인받아 전부 구현·정정.

**과정 — 잘 된 것**:
- **구체화를 먼저 하고 코드는 나중에.** "오늘 할일" 목록을 받자마자 짜지 않고, 현재 코드(3자원·리스펙·빌드셋)를 읽어 못 박은 뒤 **AskUserQuestion 4개**로 설계를 확정했다. 여기서 승천이 "프레스티지 리셋"이 아니라 **난이도 등급**이라는 게 드러났다 — 내 초기 해석대로 갔으면 트리 리셋 로직을 통째로 잘못 만들 뻔했다. 큰 방향은 코드 쓰기 전에 묻는 게 압도적으로 싸다.
- **대조 감사를 실제 데이터로.** 사용자가 트리를 짠 뒤 asset YAML을 읽어 노드 id ↔ `SkillEffects` 레지스트리를 1:1 대조. "해금해도 아무 일 안 일어나는 노드 4개", "리롤 해금 노드가 0효과", "비용 역전 없음(계열별 표로 제시)"을 근거와 함께 보고. 감으로 "괜찮아 보인다" 하지 않은 게 핵심.
- **파괴적 변경에 안전장치.** 사용자가 "트리 별로일 수도 있으니 복제해도 되냐"고 물었을 때, GUID 참조 2곳을 짚고 **(A) 백업본 유지 / (B) 새 설계 후 스왑** 두 갈래를 제시한 뒤 재배선 0인 A를 실행. 그냥 복제만 했으면 나중에 참조 꼬였을 것.
- **검증을 매번 script-execute로.** 컴파일 통과만 믿지 않고 `TierCost(0/1/2)`, `ThunderCdPerStrike=0.01`, `RerollCount=3`, 승천 배율·클램프를 실제 호출해 값으로 확인. PlayerPrefs를 건드리는 검증은 **백업→조작→원복**을 한 스크립트 안에서.

**과정 — 막힌 것 / 마찰**:
- **🔴 사용자가 작업 중 에셋을 바꿨다.** 트리 구현 도중 "잠만 스킬트리 살짝 바꿨거든, 다시 읽을래?" — 이미 읽은 YAML로 계속 갔으면 낡은 tier·선행관계로 잘못된 감사 결과를 냈을 것. 다시 읽고 **무엇이 바뀌었고 내 작업에 영향 있는지**(선행·tier 4곳 변경, 대상 노드 3개는 무영향)를 명시적으로 비교한 게 맞았다. 사람이 편집하는 에셋을 다루는 작업은 **손대기 직전에 다시 읽는 게 원칙**.
- **🟡 중간에 끼어든 요청을 놓칠 뻔.** 툴 결과와 함께 "아 지금 있는 전역 레벨 시스템도 없애줘"가 들어왔다. 마침 그 파일을 재작성하던 중이라 흡수했지만, 이미 커밋했으면 되돌아가야 했다. 대규모 재작성 중 들어온 추가 요청은 **재작성 범위에 합칠지 별도로 할지 즉시 판단**해야.
- **🟡 씬 왕복 비용.** 게임 씬(SampleScene)에만 있는 컴포넌트를 배선하려고 Title→Sample→Title로 씬을 두 번 왕복. 이름으로 `MetaRunApplier`를 못 찾아(GameManager에 부착돼 있었음) 한 번 헛쳤다. **컴포넌트는 이름이 아니라 타입으로 찾을 것**.

**AI 협업 체크**:
- 추측으로 진행? — 승천 설계에서 추측할 뻔했으나 물어서 막았다(프레스티지 vs 난이도). 반대로 **되감기 둔화 수치(50%·2초)·근거리 거리(3.5유닛)는 안 묻고 정했다** — 설명 없는 노드 텍스트라 값을 정할 근거가 없었고, "임시값이니 플레이 후 조정" 명시하고 진행. 이 정도는 물어보는 것보다 값 제시가 나았다고 봄.
- 암묵 전제? — 리롤 노드가 그랬다. "리롤 해금"과 "리롤 I"의 관계를 내가 단정하지 않고 **문제로 보고**했더니 사용자가 "당연히 해금하면 1개 주고 리롤 I이 추가"라고 확정. 사용자에게 당연한 게 코드엔 없었던 케이스.
- 자율 결정 잘한 것 — 게이팅 안전 폴백(해금 노드 없는 스킬은 통과), 백업본 A안 실행, 죽은 코드(`cost`/`costGrowth`/깊이 기반 비용)를 등급제로 교체하며 정리, 검증 시 저장 원복. 재현할 것.

**다음에 바꿀 것**:
- **[→ Kit] 사람이 편집하는 에셋(SO/씬)은 "손대기 직전에 재읽기".** 세션 중 사용자가 언제든 고칠 수 있다. 특히 감사·대조 작업은 읽은 시점과 판단 시점 사이가 벌어지면 결과가 통째로 틀어진다. 재읽기 후엔 **무엇이 바뀌었고 내 작업에 영향 있는지**를 한 줄로 비교해 보고.
- **[→ Kit] 씬 컴포넌트는 이름이 아니라 타입으로 찾을 것** (`FindObjectsByType<T>(FindObjectsInactive.Include, …)`). 스크립트명과 GameObject명이 다른 게 정상.
- **[→ Kit] 큰 방향(시스템의 정체)은 코드 전에 AskUserQuestion.** 이번 승천처럼 단어 하나("승천")가 정반대 구조를 가리킬 수 있다. 구현 규모가 클수록 선행 질문의 기대이득이 크다.

**메모**:
- 이번 세션 결과물은 **전부 컴파일·데이터 검증만** 됐고 화면·체감은 미확인. 특히 승천 UI 레이아웃은 좌표로 겹침만 검산했지 눈으로 못 봄.
- 루프가 실제로 성립하려면 **시작 캐릭터 풀 축소**가 남았다(지금은 풀이 넓어 트리 없이도 스킬이 나옴). 이걸 안 하면 "처음엔 못 깬다"가 안 만들어짐 — HANDOFF 최상단 다음 할 일로.
- Title 씬 스킬트리 패널에 죽은 UI(리셋 버튼·결정/가루 텍스트·전역레벨 바)가 남아 있음. 코드 필드를 지워 동작만 멈춘 상태라, 트리 UI 재배치 때 같이 정리 예정.
